결론: 신고 자료를 운영자 서버에 수집·저장하는 구현은 발견되지 않았다. 그러나 개인정보보호법 적합성을 확정할 수 없고, 웹접근성 완전 준수 상태도 아니다. 공개 전 확인 및 보완이 필요하다.

- WCAG 2.2 A/AA와 한국형 웹 콘텐츠 접근성 지침 2.2를 참고했다. 자동검사 통과는 전체 기준 충족이나 품질인증을 의미하지 않는다. WCAG와 KWCAG의 세부 항목도 일대일로 동일하지 않다.

### 법률 결론

**명백한 무단 수집·저장 코드는 발견되지 않았지만, 이것만으로 ‘개인정보보호법 위반 없음’을 확정할 수 없다.**

개인정보 보호법 제2조는 개인정보의 ‘처리’를 저장보다 넓게 규정한다. 운영자의 개인정보처리자 해당 여부도 업무 목적, 개인정보파일 운용, 실질적인 처리 관여 등을 확인해야 한다. 백엔드나 DB가 없다는 사실만으로 적용 제외라고 단정할 수 없다.

현재 사이트는 사용자의 기기에서 사용자가 작성하고 자신의 Gmail로 보내는 도구이므로 운영자 서버에 신고를 모으는 서비스보다 운영자 수집 범위가 제한적인 설계다. 다만 실제 운영 구성에 대한 법률적 사실관계 판단은 별도다.

### 공개 전 확인할 사항

1. **운영용 개인정보 안내/처리방침이 미완성이다.**
   현재 하단에는 요약 안내만 있고 운영자·문의 연락처, 실제 호스팅 로그, 보유 기간, 권리 행사 방법, Google 관련 처리 관계 등이 정리되지 않았다.
   법 제30조 적용 대상이면 그에 맞는 처리방침을 수립·공개해야 한다. 법 적용 여부와 별도로 Google 공개 OAuth 정책도 개인정보처리방침과 약관 링크를 요구한다.

2. **호스팅·CDN 접속 정보는 확인되지 않았다.**
   신고 내용을 저장하지 않더라도 운영 호스트가 IP, 요청 시각, User-Agent 등 접속 정보를 기록할 수 있다. 업체·기록 항목·보존 기간·운영자 열람 권한·위탁 관계를 실제 설정으로 확인해야 한다.
   ‘신고 자료를 보관하는 저장소 없음’이라는 현재 문구를 ‘어떠한 개인정보도 전혀 처리하지 않음’으로 확대해서 쓰면 안 된다.

3. **Google 통신과 국외 이전의 관계를 구체화해야 한다.**
   Google 연결 시 GIS와 OAuth 서비스, 발송 시 Gmail과 통신한다. 사용자의 기존 Gmail 이용과 운영자의 제공/위탁/국외 이전 중 어디에 해당하는지는 실제 역할과 계약, 처리 방식에 따라 검토해야 한다.
   법 제28조의8 적용 여부 및 해당되는 적법 근거를 확인해야 하며, API 사용만으로 곧바로 위반이라고 할 수도, 사용자의 ‘메일 발송 동의’ 체크만으로 모든 법적 동의가 해결된다고 할 수도 없다.

4. **신고 대상자와 제3자의 정보 최소화가 필요하다.**
   계정·닉네임·이미지·영상은 개인을 알아볼 수 있으면 개인정보가 될 수 있다. 신고와 무관한 전화번호, 주소, 주민등록번호, 제3자 대화·얼굴 등은 제외/가림을 권장하는 안내가 적절하다.
   신고자가 발송에 동의했다는 이유만으로 다른 사람의 개인정보 제공 근거까지 자동 확보되는 것은 아니다. 실제 자료의 정당성은 개별 사안에 따라 달라진다.

5. **‘기기에서 임시 보관’의 범위를 분명하게 유지해야 한다.**
   앱은 파일을 기기에 별도 저장하지 않고 선택한 원본 파일을 읽는다. 메일을 보내면 Google과 수신자에게 전달되므로 ‘자료가 언제나 기기 밖으로 나가지 않는다’고 표현하면 부정확하다.
   현재 하단은 발송 메일이 보낸메일함·수신자 메일함에 남는 점을 안내하므로 이 부분은 적절하다. 브라우저 뒤로가기 캐시/세션 복원까지 앱이 확실히 통제한다는 보장은 하지 않는 것이 좋다.

개인정보보호법 위반 여부에 대한 최종 판정이나 법률 자문을 대신하는 보고서는 아니다. 운영 주체와 호스팅·Google 처리 관계를 확정한 뒤 필요한 법률 검토를 받는 것이 적절하다.

## 3. 웹접근성 발견 사항

### A01. 입력칸 테두리 대비 부족 — 우선 수정

- 위치: src/style.scss:30
- 테두리 #aab2bc / 배경 #ffffff = 약 2.142:1.
- 비활성 입력이 아닌 일반 텍스트 입력·본문 입력칸에 적용된다.
- 빈 입력칸의 경계를 식별하는 시각 정보가 약하다. WCAG 2.2 1.4.11 AA는 필요한 UI 식별 정보의 대비를 3:1 이상으로 요구한다.
- 권고: 흰 배경에서 3:1 이상이 되는 테두리 색상으로 변경. 일반 상태·포커스·오류 상태를 함께 검토.
- 구분: 단순 장식 구획선까지 모두 3:1이어야 한다는 뜻은 아니다.

### A02. 최종 확인 대화상자에 접근 가능한 이름 없음 — 우선 수정

- 위치: src/App.tsx:88
- native dialog에 aria-labelledby 또는 aria-label 없음.
- 접근성 트리에서 ‘dialog:’ 뒤 이름이 없고, 제목은 별도의 heading으로만 존재함을 확인했다.
- WCAG 4.1.2 및 W3C 모달 대화상자 패턴 관점에서 창 목적을 알리는 이름 연결이 필요하다.
- 권고: 제목 h2에 id를 부여하고 dialog의 aria-labelledby로 연결.
- 기본 포커스는 본문 확인 summary로 이동했다. 제목 또는 ‘돌아가서 수정’에 초기 포커스를 명시하면 수신 정보 확인 흐름이 더 명확하다.
- Escape 닫기와 호출 버튼으로 포커스 복귀는 확인했다.
- Tab 이동 중 브라우저 본문/브라우저 UI 경계를 경유하는 관찰이 있었지만 배경 입력으로 이동한 것은 확인되지 않았다. 이것만으로 포커스 트랩 실패라고 단정하지 않았다. 실제 스크린리더 조합의 추가 검사가 필요하다.

### A03. 필수 항목 상태와 오류 안내 연결 보완 — 권고

- 위치: src/App.tsx:37, 67~70, 85
- ‘필수’ 텍스트 배지는 있으나 해당 input/textarea에 required 또는 aria-required가 없다.
- 검증 실패 시 role=status로 텍스트를 알려 주지만 잘못된 항목에 포커스를 옮기거나 aria-invalid/aria-describedby로 오류를 연결하지 않는다.
- 수신 주소·CC·BCC 중 어떤 입력이 틀렸는지도 통합 문구만 제공한다.
- 권고: 필수 상태를 프로그램적으로 표시하고, 항목별 오류를 인접하게 제공하며 첫 오류로 이동. CC와 BCC 설명도 aria-describedby로 연결.
- 텍스트 오류 안내가 존재하므로, required 속성이 없다는 사실만으로 모든 관련 WCAG 항목이 자동 실패한다고 판정하지는 않았다.

### A04. 작은 글씨 및 모바일 입력 사용성 — 권고

- 배지/영문 보조 문구 약 10px, 설명·개인정보 본문 약 11px, 일반 입력 13px, 메일 본문 12px.
- 작은 글씨 자체가 곧 WCAG 위반이라는 일반 규칙은 없다. 다만 장문 읽기·저시력·모바일 가독성에는 불리하다.
- 압축된 배치는 유지하되 모바일 본문/입력 14~16px 수준을 검토.
- iOS 입력 포커스 확대 및 소프트 키보드에 의한 화면 가림은 실제 기기 미검증 사항이다.

### A05. 작은 화면 + 글자 확대 시 날짜/시간 영역 넘침 — 권고 / 추가 검증

- 기본 320px에서는 가로 넘침이 없었다.
- 1280px에서 계산된 글자 크기를 200%로 변경한 모의검사: 가로 넘침 없음.
- 320px에서 같은 글자 확대 모의검사: 문서 너비 462px로 증가, 시간 입력 영역이 화면 밖으로 확장.
- 권고: 날짜/시간 2열을 좁은 화면 또는 큰 글자 설정에서는 1열로 재배치.
- 이는 브라우저 실제 줌 시험이 아닌 CSS 글자 확대 모의검사다. 가로 스크롤 발생 하나만으로 1.4.4 실패를 확정하지 않으며, 실제 기기에서 기능·내용 손실과 확대 동작을 추가 확인해야 한다.

- 초기 화면 수동 확인 항목 1개: 화살표 문자만 있는 span의 대비 자동 판단 불가. 흰색/남색 조합이며 버튼 본문과 중복하는 장식이다.
- 정적 빌드의 확인창 검사에서는 자동 위반 및 incomplete 0.
- 그러나 자동검사가 A01/A02를 잡지 못했다. 따라서 0건을 근거로 완전 준수라고 표시하면 안 된다.
- html-validate 11.18.0 standard preset: 개발 화면 DOM 및 정적 빌드 DOM 모두 오류 0.
- 이는 W3C 공식 인증/전체 CSS 인증/모든 동적 상태의 HTML 검증을 뜻하지 않는다.
- React/TypeScript 빌드 성공.
- 기존 메일·공식 양식 테스트 7개 통과.
- npm audit --omit=dev: 확인 시점 알려진 운영 의존성 취약점 0.
- CSS 전체 표준 검사, 실제 Safari/Firefox 호환성은 수행하지 않았다. native dialog, date/time 입력, 90dvh 등의 동작은 실제 지원 브라우저에서 확인해야 한다.
- form 요소가 없다는 사실만으로 HTML 표준 위반은 아니다. 현재는 버튼 이벤트와 자체 검증으로 처리하고 있다.

- 실제 호스팅 업체·로그·개인정보 처리 관계 확정 및 방침/문의 창구 마련.
